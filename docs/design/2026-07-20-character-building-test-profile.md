# Character Building 式测试 Agent 初始画像设计

## 1. 背景

DREAM 面向公司的银行聊天 Agent，负责从 Agent 的任务与会话中提炼两类长期产物：

- Agent 级 AI 决策卡与周期整理后的决策规则；
- 用户级、相互隔离并持续更新的用户画像。

公司的真实 Agent 很可能已经拥有初始身份、系统提示词和合规规则，但当前无法取得其源码或配置。因此，本阶段不能验证 DREAM 与真实初始画像的集成，也不应重新开发一套生产画像管理系统。

为了完成可控的进化前后对照实验，本设计借鉴 Character Building 的角色构建方式，生成一份较完整、可检查且固定不变的测试 Agent 初始画像。它只作为实验基线，不代表公司的真实 Agent。

## 2. 目标

本阶段实现以下闭环：

1. 内部测试人员填写少量结构化字段；
2. 大模型依据这些字段生成完整初始画像草稿；
3. DREAM 对草稿进行结构、来源和安全校验；
4. 人工确认后，将画像锁定为固定测试基线；
5. 使用相同初始画像、相同底层模型和相同参数完成进化前后对照；
6. 只有 `USER.md`、AI 决策卡和 `DECISION_RULES.md` 在实验中持续更新；
7. 通过画像哈希证明初始画像在整个实验期间没有变化。

## 3. 非目标

本阶段不实现：

- 公司的正式银行 Agent 初始画像管理系统；
- 面向银行客户的 Agent 创建入口；
- 对公司已有 System Prompt 或合规策略的替代；
- 与真实账户、交易或客户数据的连接；
- 自动修改或自动发布生产 Agent 的初始画像；
- 依赖 Character.AI 网站、非公开接口或网站回写完成实验。

## 4. 核心边界

### 4.1 画像属于 Agent，不属于底层大模型

测试初始画像描述的是逻辑 Agent。豆包、DeepSeek 或其他 OpenAI-compatible 模型只是可替换的推理与生成引擎。

```text
固定测试初始画像
      +
DREAM 决策规则
      +
当前用户画像
      ↓
测试 Agent 上下文
      ↓
外部大模型
```

更换底层模型不会改变画像、决策卡或用户画像的归属。

### 4.2 初始画像与进化产物分离

| 内容 | 文件 | 变化规则 |
|---|---|---|
| 测试 Agent 初始画像 | `TEST_AGENT_PROFILE.md` | 人工批准后锁定，实验期间不变 |
| AI 决策卡 | `decision-cards/*.md` | 从任务经历中持续生成 |
| AI 决策规则 | `DECISION_RULES.md` | 由 AI Curator 周期整理 |
| 用户画像 | `users/<user_id>/USER.md` | 从该用户会话中持续更新 |
| 测试用户服务上下文 | 上述文件的运行时组合 | 每个新任务重新读取 |

做梦流程不得修改 `TEST_AGENT_PROFILE.md`。如果发现初始画像存在问题，只记录建议，不在本次实验中自动修改。

### 4.3 安全边界优先

测试画像中的安全边界优先于学习得到的决策规则。决策卡不得形成与下列规则冲突的经验：

- 索要密码、验证码或完整银行卡号；
- 伪造账户状态、交易结果或审批结果；
- 保证贷款审批或投资收益；
- 代替客户执行真实资金操作；
- 将某个用户的身份、偏好或任务内容写入 Agent 级规则。

本阶段使用的是测试安全边界，不声称覆盖银行正式合规要求。

## 5. Character Building 字段映射

采用“快速创建 + 高级定义 + 示例对话 + 测试发布”的构建逻辑。

### 5.1 快速创建字段

| 字段 | 类型 | 必填 | 用途 |
|---|---|---:|---|
| `name` | string | 是 | Agent 展示名称 |
| `tagline` | string | 是 | 一句话说明 Agent 的定位 |
| `role` | string | 是 | Agent 在测试中的服务身份 |
| `service_scope` | string[] | 是 | 允许回答的业务范围 |
| `personality` | string[] | 是 | 可观察的性格与行为倾向 |
| `response_style` | string[] | 是 | 回答结构和表达方式 |
| `greeting` | string | 否 | 测试会话开场白；为空时由生成器起草 |

### 5.2 高级画像章节

完整画像必须包含以下 Markdown 章节：

1. 简短定位；
2. 身份与职责；
3. 核心目标；
4. 性格与行为；
5. 服务范围；
6. 回答风格；
7. 安全边界；
8. 转人工条件；
9. 开场白；
10. 示例对话。

### 5.3 示例对话

生成的画像至少包含四类示例：

- 普通业务咨询；
- 敏感信息保护；
- 信息不足或无法确认；
- 涉及资金风险时转接人工。

示例只用于表现可观察的回答方式，不包含模型内部思维过程，不使用真实银行名称、真实客户信息或真实交易数据。

## 6. 生成流程

### 6.1 结构化输入

测试人员填写一个严格校验的输入对象：

```json
{
  "name": "小银",
  "tagline": "可靠、清晰的银行业务智能助手",
  "role": "银行智能客服",
  "service_scope": [
    "银行卡常见问题",
    "转账流程说明",
    "手机银行操作指引",
    "存款产品基础介绍"
  ],
  "personality": ["专业", "耐心", "谨慎", "有边界感"],
  "response_style": [
    "先回答核心问题",
    "再给操作步骤",
    "风险信息单独提醒"
  ]
}
```

输入字段禁止出现真实客户数据、真实密钥、真实账户信息或未经确认的银行内部政策。

### 6.2 大模型生成草稿

生成器只接收上述结构化输入和固定生成提示词，返回一份 Markdown 草稿。生成结果必须标记为 `draft`，不能直接参与正式实验。

大模型可以：

- 将简短字段扩展成完整、自然的角色说明；
- 补充符合输入的开场白；
- 按规定场景起草示例对话；
- 将抽象性格转成可观察的回答行为。

大模型不得：

- 添加输入中没有的银行名称、产品、费率或业务承诺；
- 声称拥有真实账户访问或交易执行能力；
- 生成与测试安全边界冲突的内容；
- 自行把画像标记为已批准或已激活。

### 6.3 自动校验

DREAM 在人工审批前检查：

- 必需字段和章节完整；
- 文件是合法、非空的 UTF-8 Markdown；
- 不含 NUL、密钥形态或明显的真实账户数据；
- 服务范围、性格和表达风格能够追溯到输入字段；
- 至少包含四类示例对话；
- 不包含保证收益、保证审批或索要认证凭据的语句；
- 文件大小不超过配置上限；
- 草稿状态不能被任务启动流程读取。

### 6.4 人工确认与锁定

人工确认后：

- 将状态由 `draft` 改为 `approved`；
- 保存批准人、批准时间、版本号和 SHA-256；
- 生成实验使用的 `TEST_AGENT_PROFILE.md`；
- 在本轮实验结束前禁止覆盖；
- 修改画像必须创建新的实验运行，不能在同一次前后对照中途切换。

## 7. 文件结构

建议的测试文件结构为：

```text
tests/fixtures/agent_profile/
├── bank-assistant.input.json
├── bank-assistant.approved.md
└── bank-assistant.approval.json
```

运行时复制到隔离的测试目录：

```text
validation-run/
├── TEST_AGENT_PROFILE.md
├── decision-cards/
├── DECISION_RULES.md
└── users/<user_id>/USER.md
```

输入 JSON 是生成参数，Markdown 是实际上下文，审批 JSON 只保存版本、状态、哈希和时间，不保存额外画像内容。

## 8. 进化前后对照

### 8.1 进化前

```text
TEST_AGENT_PROFILE.md
        +
当前测试任务
        ↓
固定底层模型与固定参数
        ↓
基线回答
```

### 8.2 进化后

```text
同一份 TEST_AGENT_PROFILE.md
        +
最新 DECISION_RULES.md
        +
当前用户 USER.md
        +
新测试任务
        ↓
同一底层模型与固定参数
        ↓
进化后回答
```

评估报告必须记录初始画像 SHA-256。进化前后哈希不一致时，本轮对照自动判定无效。

## 9. 与现有 Character.AI 验证代码的关系

本设计借鉴 Character Building 的结构，不依赖 Character.AI 网站运行。

现有 `CHARACTER_DEFINITION.md` 和 `USER_PERSONA.md` 回写逻辑保留为可选验证适配器，在缺少公司 Agent 的情况下不作为主要验收依据。主要验收改为：同一个外部大模型在固定测试画像下，加载 DREAM 产物前后的行为差异。

以后取得公司 Agent 接口后：

- 用公司已有初始画像替换 `TEST_AGENT_PROFILE.md`；
- 用公司 Agent 的上下文接口替换测试上下文组装器；
- 保留 DREAM 的会话导入、用户画像、决策卡、做梦、版本、快照和回滚能力。

## 10. 验收标准

测试画像生成能力通过以下条件验收：

- 输入字段全部经过结构校验；
- 生成 Markdown 包含全部必需章节；
- 至少包含四类规定示例；
- 未引入输入之外的真实银行事实或业务承诺；
- 草稿不能直接用于任务；
- 人工批准后产生可验证的版本和哈希；
- 同一次进化实验中的初始画像哈希保持不变；
- 三个模拟用户的用户画像仍按 `user_id` 隔离；
- Agent 级决策卡不包含某个用户的私人信息；
- 至少完成两轮“任务—提炼—做梦—下一任务使用”；
- 最终评价能够区分初始画像效果、用户画像效果和决策规则效果。

## 11. 后续实现范围

设计通过后，仅新增测试画像生成与校验能力，不建设生产管理页面。实现范围包括：

- 结构化输入模型；
- 可替换的大模型画像草稿生成后端；
- Markdown 校验器；
- 人工批准与哈希锁定；
- 测试上下文组合器；
- 对应的单元测试和离线固定样例；
- 在正式评价报告中记录初始画像版本和哈希。
